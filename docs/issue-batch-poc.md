# Asset-first Issue Batch POC

The old Asset Request, requirement-line, and allocation domain was permanently removed by migration `20260908120000_asset_first_issue_batches`. Controlled migration `20260908190000_legacy_poc_cleanup` subsequently removed 58 inactive automated fixture Assets and their 15 closed assignments, 20 movements, and one inactive EPC. It also removed exact inactive test masters, the unused BladeSku/Machine schema, and obsolete Issue Batch return-initiation/swap columns. Current Issue Batch history and the retained operational/manual Assets were not deleted.

Assets is the operational starting point. Eligible Assets are active, `AVAILABLE`, have an active EPC, and have an active verified home location. Confirming Prepare Issue validates Recipient and direct operational To Location for every selected Asset, reserves them all, creates active Assignments, and advances them to `ISSUED` / `PENDING_CONFIRMATION` in one serializable all-or-nothing transaction. `RESERVED` remains an internal concurrency state rather than a Store-facing step.

New Issue Batch items use `RESERVED -> ISSUED -> CONFIRMED -> RETURNED`; cancellation is historical. New Assets use `AVAILABLE -> RESERVED -> PENDING_CONFIRMATION -> IN_USE -> AVAILABLE`. The dummy AST-001 graph and the obsolete `RETURN_PENDING` states were removed by migration `20260908200000_remove_dummy_ast001_return_pending`.

Preparation creates an active Assignment but does not change verified location or create a movement. `POST /api/issue-batches/:id/scan-comparison` supports batch Scan All, while `POST /api/issue-batches/items/:itemId/confirm-issue` validates one row against its exact expected Asset. Only expected EPC matches mutate state. Successful confirmation creates exactly one movement and structured Web Admin scan confirmation. Cancelling an unconfirmed item is terminal: its item becomes `CANCELLED`, its Assignment is closed, and its Asset becomes `AVAILABLE` without movement or confirmation.

Normal Store return uses `POST /api/issue-batches/return-scan`. Every EPC is processed in its own serializable transaction, so one scan can return confirmed Assets from different batches without invalid EPCs rolling back valid returns. A successful scan closes the active Assignment, returns the item directly from `CONFIRMED` to `RETURNED`, preserves condition, moves the Asset from `IN_USE` to `AVAILABLE` at its active storage-compatible home, and creates the physical movement and structured scan confirmation. The obsolete Issue Batch initiate-return, confirm-return, and swap APIs were removed.

Assignment read APIs remain for audit. General Assignment mutation and legacy recovery APIs have been removed; all operational assignment transitions now occur through Issue Batch services.
